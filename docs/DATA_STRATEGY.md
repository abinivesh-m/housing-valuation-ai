# Data strategy

This document states exactly what data the engine uses today, what it does **not** use, and the
sequence in which real data would replace the synthetic corpus. It is written for a diligence
review, so every claim is tagged with a status: **live**, **synthetic**, or **planned**.

---

## 1. What is live in this build

| Dataset | Status | Used for | Terms |
|---|---|---|---|
| Parametric property corpus, 6,000 rows, seed `20261110` | **synthetic** — generated by `data_gen.py` in this repo | Training, conformal calibration, holdout evaluation, comparable pool (3,000 rows) | This repo's MIT licence |
| Micro-market coordinates, 64 localities / 8 cities | **approximate** — hand-entered locality centroids | Comparable distance, map centring, geo-enrichment anchor | Coordinates are rounded to ~4 decimal places and are not parcel-level |
| OpenStreetMap POI density via Overpass API | **live external** | Metro / school / hospital / highway counts within 1.5 km, returned in the geo panel | ODbL 1.0, attribution rendered in the UI; volunteer endpoint, no SLA |

That is the complete list. Nothing else in the running system is external data.

### Why the corpus is synthetic, and what that means

There is no national, redistributable, transaction-level property dataset in India. State
registration records are fragmented across 28+ registrar systems, most have no bulk API, and the
ones that do license data do so under contracts that prohibit redistribution. Scraping listing
portals would breach their terms and would also be the wrong data: asking prices are not sale
prices.

So the corpus is a **documented parametric price surface**:

```
price = city_rate × locality_index × type_multiplier
      × area
      × bedroom_premium        (1 + 4.5% per bedroom beyond the first)
      × floor_premium          (1 + 10% × floor/total_floors, only if > 3 storeys)
      × depreciation           (1.1%/yr for 15 years, then 0.55%/yr, floored at 0.55)
      × furnishing_multiplier
      × exp distance decay     (metro −1/1.8 km, school −1/1.5 km,
                                hospital −1/2.0 km, highway −1/3.0 km)
      × amenity factors        (lift, parking, balcony, crime index)
      × tenure / occupancy factors
      × lognormal noise        (σ = 8.5% residential, 13% commercial)
```

Coefficients are hand-set in `data_gen.py` and visible in the source, with a price floor of ₹8.5 lakh
residential and ₹12 lakh commercial. This makes the corpus **reproducible and inspectable**, which is
what a prototype needs: the feature contract, the model, the calibration, the attribution, the
comparable reconciliation, the policy layer and the audit chain can all be exercised end to end. It
does **not** make the accuracy figures evidence about the Indian housing market. Every number in
`README.md` and `MODEL_CARD.md` is within-corpus.

Latitude and longitude are included so that the comparable engine, the haversine filter and the
Overpass call run against real geography rather than a stub. That is the only reason they are there.

## 2. What is deliberately absent

| Excluded | Reason |
|---|---|
| Scraped listing prices (99acres, MagicBricks, Housing.com) | Terms of service prohibit it; asking prices are biased upward and stale |
| Aadhaar, PAN, borrower name, income, caste, religion, gender | Not needed to value a property; using them would create fair-lending exposure |
| Aadhaar-linked land records | Not publicly accessible; legal constraints |
| Satellite built-up area | Specified below as a production feature — **not faked with a proxy** in this build |
| Rental / yield data | No open, licensed source; commercial valuation needs it and this build says so |
| Crime index from a live feed | The feature exists in the model, but production requires a citable district-level source; today it is an input field, clearly labelled |

## 3. Production data plan

Three phases. Each phase lists the source class, what it unlocks, and the principal obstacle.
Portal names are given as starting points; access terms change and must be confirmed at contracting
time.

### Phase 1 — transaction truth (months 0–3)

The single highest-value dataset is **registered sale deeds with consideration amount**. Everything
else is a feature.

| Source | What it gives | Obstacle |
|---|---|---|
| State registration departments — e.g. IGR Maharashtra (e-Search, Ready Reckoner), Karnataka (Kaveri 2.0, guidance value), Telangana (Dharani / IGRS), Tamil Nadu (TNREGINET, guideline value), Delhi DOR (circle rates), Gujarat (e-Dhara, jantri), West Bengal (e-Nathikaran), Uttar Pradesh (IGRSUP) | Consideration amount, execution date, parties (to be dropped), survey/plot identifiers, property description | State-by-state schema, no uniform API, fees per search, some require an MoU or authorised aggregator |
| Authorised data aggregators and title-search firms | Normalised deed feed across states, encumbrance and litigation flags | Commercial contract; per-lookup cost; coverage gaps in tier-3 districts |
| Circle / guidance / jantri rates | A **floor**, not a market price | Published annually; systematically below market in appreciating micro-markets |
| NHB RESIDEX and RBI House Price Index | City-level quarterly index for time adjustment and drift monitoring | Index level only — cannot price an individual property |

Two things must be built on top of the raw deed feed before it can train a model:

1. **Property identity resolution.** Deeds describe the same flat inconsistently across
   registrations. Requires address normalisation, survey/plot matching, and — where available —
   the **ULPIN** parcel identifier being rolled out under DILRMP, or the municipal property-tax
   assessment number. Without this, repeat sales cannot be paired.
2. **Label cleaning.** See §4. A deed price is not automatically a market price.

### Phase 2 — physical truth (months 3–9)

Declared area is the largest single source of real-world AVM error, and it is the one thing the
current build takes at face value.

| Source | What it gives | Notes |
|---|---|---|
| Sentinel-2 (ESA Copernicus) | 10 m multispectral, ~5-day revisit, free and open | Roof footprint and change detection; vegetation/water context |
| Sentinel-1 SAR | All-weather C-band | Monsoon-season construction change where optical is cloud-covered |
| Google Open Buildings | Open building footprints with temporal signals | Useful for footprint area and new-construction detection |
| ISRO Bhuvan / Bhoonidhi | Indian LULC, administrative boundaries, some high-resolution products | Domestic coverage and alignment with Indian administrative units |

Deliverable: a **built-up-area estimate with a confidence band**, cross-checked against the declared
area. A mismatch beyond a threshold becomes a policy flag (`AREA_MISMATCH`) rather than a silent
adjustment. This is the feature that most improves real-world accuracy, and it is explicitly not
present in the prototype.

### Phase 3 — market texture (months 9–18)

| Source | What it gives | Obstacle |
|---|---|---|
| Licensed portal feed (asking prices, time-on-market) | Liquidity, reprice velocity, seller expectations | Commercial licence; must be used as a *signal*, not a label |
| Rental listings / lease registrations | Yield for the income approach on commercial assets | Lease registration is sparse; listings are ToS-restricted |
| Municipal property-tax records | Built-up area, usage, assessment history | City-by-city, often offline; useful for identity resolution |
| Infrastructure pipeline (metro alignment, ring roads) | Forward-looking accessibility features | Project timelines slip; must be time-stamped to avoid look-ahead leakage |

## 4. Label quality — the part most prototypes skip

A registered consideration amount is an imperfect target. Four biases must be handled explicitly:

| Bias | Effect | Treatment |
|---|---|---|
| **Circle-rate anchoring** | Deeds are frequently registered at or near the circle rate to reduce stamp duty, so recorded prices understate market value | Model the ratio `deed / circle rate` and winsorise the bottom tail; flag districts where the ratio clusters at 1.0 |
| **Delayed registration** | 3–24 months between agreement and registration | Time-adjust to the agreement date where available, else to the registration month using the city index |
| **Area definition** | Carpet, built-up and super built-up differ by 15–30% | Normalise to a single definition; treat the conversion factor as a feature with a district prior |
| **Unrecorded attributes** | Renovation quality, view, floor plate, legal encumbrance | Cannot be recovered from deeds alone; captured through the inspection path and used to calibrate the interval, not the point estimate |

Paired resales (same property, two dates) are the cleanest validation set because property
attributes cancel. They are also the scarcest, which is why identity resolution matters.

## 5. Validation protocol for a real feed

The corpus-level evaluation in `MODEL_CARD.md` is not sufficient for production. The protocol:

1. **Out-of-time holdout.** Train on all deeds registered before `T − 12 months`; test on the most
   recent 12 months. Random splits leak market regime into the test set.
2. **Grouped holdout by locality.** Already implemented (`GroupKFold(5) by locality`), because a
   model that has memorised a micro-market will look excellent on a random split and fail on a new
   one.
3. **Geographic holdout by city.** Train without one entire city; measure transfer. This is the
   realistic test for expansion.
4. **Coverage-first reporting.** Publish the share of properties that meet the desktop-decision
   criteria before publishing MAPE. An AVM that is accurate on 40% of stock and silent on the rest
   is a different product from one that covers 90%.
5. **Conformal recalibration on a rolling window.** Recompute residual quantiles quarterly on the
   most recent out-of-fold data; do not freeze calibration from launch day.
6. **Paired-sales audit.** A random monthly sample of matched resales, scored blind.
7. **Segment reporting.** By price band, property type, city and locality tier — never a single
   headline number. The current build already reports five price bands.
8. **Bias monitoring.** No protected attributes enter the model. Monitor approval and error rates
   by geography and by proxy variables (locality income tier) for disparate impact.

Gates before any production use: coverage ≥ 70% of target stock, median APE ≤ 8% on the out-of-time
holdout, empirical interval coverage within 3 points of nominal, no segment with MAPE above 15%
without an automatic referral rule.

## 6. Privacy and compliance

- **Data minimisation.** The engine consumes property attributes only. Party names, contact details
  and identifiers from deeds are stripped at ingestion and never written to the audit ledger.
- **Audit content.** Each ledger entry stores the valuation inputs that matter for replay
  (city, locality, type, area, age), the outputs, and a SHA-256 payload digest. No personal data.
- **DPDP Act 2023.** Any workflow that touches personal data (applicant KYC, document collection)
  sits outside this engine and must meet the Act's notice, consent, purpose-limitation and
  retention obligations. This repository does not process personal data.
- **Data-sharing agreements.** State registry and aggregator feeds must be used within the scope of
  their licence; derived features may be retainable where raw records are not. This distinction
  must be settled contractually before training.
- **Model governance.** A model that informs credit collateral is a regulated activity in most
  jurisdictions. The engine produces a policy position and a reason-coded explanation; the lender
  remains the decision-maker and is responsible for validation, documentation and fair-lending
  review.

## 7. Cost model

Per-valuation data cost is dominated by three line items, none of which is asserted as a number
here because all three are contractual:

1. Registry search fee (per deed, per state).
2. Aggregator licence (per lookup or annual minimum).
3. Imagery processing (storage + compute for footprint change detection; imagery itself is free at
   Sentinel resolution).

The design keeps the marginal cost low by caching locality-level statistics and only resolving a
deed-level comparable set when the property is actually being valued. The current build's 55 ms
serving latency is a *model* cost, not a data cost; production latency will be dominated by the
registry call, which is why the API is designed to return a valuation and enrich it asynchronously.

---

## 8. What this build proves, restated

It proves the **system**: a feature contract that a real feed can populate, a model that beats the
rate-card baseline on identical rows, calibrated intervals, exact attribution, a comparable engine
with an independent adjustment grid, a policy layer with named checks, and a tamper-evident trail.

It does not prove the **market**. That requires phase 1 data, identity resolution, out-of-time
validation, and a lender willing to run a shadow-mode pilot against human valuations. The honest
next step is a 90-day shadow deployment on one city and one property type, comparing the engine
against the lender's own valuers on the same files.
